## ۱. ارزیابی از دیدگاه کاربر نهایی (End-User Persona Perspective)

### ۱.۱. پرسونای مدیر پروژه / دستگاه نظارت (Project Manager / Supervisor Persona)
* **محاسبه غلط جمع کل در تغییر صفحه (Defect DEF-B04-01 / Group E14):**
  هنگامی که ناظر در صفحه «بانک فعالیت‌ها» (`/projects/:projectId/activity-log`) فیلتری اعمال می‌کند که بیش از ۵۰ ردیف نتیجه دارد (مثلاً ۵۱ ردیف):
  - در صفحه اول، نوار خلاصه بالا عدد ۵۰ را به عنوان مجموع نفرات نشان می‌دهد.
  - با رفتن به صفحه دوم، مجموع نفرات ناگهان به عدد ۱ تغییر می‌کند!
  - کاربر متوجه می‌شود که ارقام سرجمع بالای صفحه «جمع کل نتایج فیلتر» نیست، بلکه صرفاً جمع ۵۰ سطرِ صفحه جاری است. این رفتار برای تصمیم‌گیری کلان پروژه کاملاً گمراه‌کننده و نامعتبر است.
* **اختلاف میان مقادیر نمایش‌داده‌شده در UI و فایل خروجی اکسل (Defect DEF-B04-02 / Groups E11 & E14):**
  کاربر دکمه «خروجی اکسل دیتابیس جامع فعالیت‌ها (FILE 1)» را می‌زند و فایلی با ۵۱ ردیف دریافت می‌کند. جمع احجام و نفرات در فایل اکسل با ارقام درج‌شده در بالای صفحه وب تفاوت دارد، زیرا اکسل تمام ۵۱ سطر را صادر کرده در حالی که UI فقط سطر‌های صفحه جاری را جمع زده است.

### ۱.۲. پرسونای سرپرست دفتر فنی و برنامه‌ریزی (Technical Office / Planning Engineer)
* **فقدان فیلترهای استاندارد کارگاهی در فهرست گزارش‌های روزانه (Defect DEF-B04-03 / Group E12):**
  در فهرست گزارش‌های روزانه (`/projects/:projectId/daily-reports`):
  - کاربر نیاز دارد گزارش‌ها را بر اساس دیسیپلین، پیمانکار یا بلوک فیلتر کند (طبق الزامات FR016).
  - در حال حاضر رابط کاربری و API این مسیر فقط فیلترهای `date_from`، `date_to` و `status` را دارند. هیچ انتخابی برای `discipline`، `contractor` و `block` در فهرست روزانه تعبیه نشده است.
* **اشتراک‌گذاری لینک (Shareable URL) و بازگشت در مرورگر (Browser Navigation / Group E13):**
  هنگامی که مهندس دفتر فنی لینک گزارش فعالیت فیلترشده را برای مدیر پروژه ارسال می‌کند، برخی فیلترهای چندگزینه‌ای (مثل آرایه‌های دیسیپلین و قطعه) به درستی در URL قرار می‌گیرند، اما به دلیل استفاده از حالت `replace: true` در ناوبری و عدم اعتبارسنجی مقادیر متناقض با پروژه (مثلاً شناسه‌های خارج از پروژه)، رفتار دکمه بازگشت مرورگر (Back button) تاریخچه جستجو را تخریب می‌کند.

### ۱.۳. پرسونای مأمور کنترل کیفیت و داده (QA & Data Auditor)
* **جمع نامعتبر احجام با واحدهای ناسازگار یا مقادیر نامعلوم (Defect DEF-B04-04 / Groups D05 & E14):**
  در سطر فعالیت‌ها، اگر مقدار عددی حجمی برای فعالیتی ثبت نشده باشد (null / not-measured)، نباید به عنوان صفر قطعی تلقی شود یا خطای محاسباتی ایجاد کند. در UI کنونی، فیلتر مقادیر بر اساس واحدهای اندازه‌گیری صرفاً بر روی ردیف‌های صفحه ۵۰تایی اجرا می‌شود و اگر در صفحه دوم واحدهای جدیدی وجود داشته باشند، در نمای صفحه اول اصلاً پدیدار نمی‌شوند.
* **عنوان گمراه‌کننده نفر-روز (Defect DEF-B04-05 / Group D07):**
  نوار خلاصه رابط کاربری عبارت «مجموع نفرات (نفر-روز):» را درج کرده است. این مقدار صرفاً حاصل‌جمع جبری ستون `headcount` سطرهای فعالیت است و نفر-روز واقعی (شامل ساعات کاری، شیفت و حضور یکتای پرسنل) نیست. طبق تصمیم D07 و دستورالعمل، تبدیل لفظی جمع سطرها به «نفر-روز» خلاف واقع بوده و باید با برچسب دقیق اصلاح شود.

## ۲. ارزیابی انطباق فنی و تضمین کیفیت (QA Technical Findings)

### ۲.۱. بررسی پایداری و در دسترس بودن سرورها (:5173 و :8000)
- سرویس‌های وب (Vite: 5173) و بک‌اند (Django: 8000) به دلیل محیط ایزوله در وضعیت خاموش قرار دارند (`curl` به پورت‌های محلی با خطای connection refused مواجه شد).
- کلیه بررسی‌ها از طریق تحلیل جامع سورس‌کد، بازبینی تست‌های واحد و فایل‌های شواهد ممیزی مستقر در `output/a1-requirements-2026-11-18/evidence/` اعتبارسنجی گردید.

### ۲.۲. تحلیل کدهای فرانت‌اند (`apps/web`)
1. **فایل `apps/web/src/app/routes/project-activity-log.tsx`:**
   - خطوط ۱۲۴ تا ۱۳۵:
     ```typescript
     const rows = data?.results ?? [];
     const totalHeadcount = useMemo(() => {
       return rows.reduce((acc, r) => acc + (Number(r.headcount) || 0), 0);
     }, [rows]);
     const quantitiesByUnit = useMemo(() => {
       const map: Record<string, number> = {};
       for (const r of rows) {
         if (r.unit && r.quantity != null && !isNaN(Number(r.quantity))) {
           map[r.unit] = (map[r.unit] || 0) + Number(r.quantity);
         }
       }
       return map;
     }, [rows]);
     ```
   - **شکاف عمده:** `rows` صرفاً شامل `data.results` (۵۰ رکورد یک صفحه) است. سرجمع کل از سرور دریافت نمی‌شود، بلکه در سمت مرورگر روی ۵۰ رکورد جاری محاسبه می‌گردد.
2. **فایل `apps/web/src/app/routes/daily-reports-list.tsx`:**
   - خطوط ۸۹ تا ۱۰۰:
     تنها فیلترهای `page`، `per_page`، `date_from`، `date_to` و `status` استخراج و به API فرستاده می‌شوند. پارامترهای دیسیپلین، بلوک و پیمانکار هیچ‌گونه المان UI یا ارسال پارامتر به بک‌اند ندارند.

### ۲.۳. تحلیل کدهای بک‌اند (`apps/api`)
1. **فایل `apps/api/core/field_reports/report_views.py` (`ActivityLogView`):**
   - ویو از `ReportPagination` استاندارد DRF استفاده کرده و خروجی پیجینیشن معمولی شامل `count`, `next`, `previous`, `results` تولید می‌کند.
   - هیچ ساختار تجمیعی (`totals`, `aggregates`, `quantities_by_unit`, `total_headcount`) روی کل `queryset` محاسبه و به Response تزریق نمی‌شود.
2. **فایل `apps/api/core/field_reports/daily_report_views.py` (`DailyReportViewSet.get_queryset`):**
   - متد `get_queryset` در فیلتر گزارش‌های روزانه پارامترهای `discipline`، `contractor` و `block` را اعمال نمی‌کند.
3. **پروب تجربی موجود در شواهد ممیزی (`output/a1-requirements-2026-11-18/evidence/pagination-probe.json`):**
   - گواهی نقص ثبت‌شده:
     ```json
     {
       "count": 51,
       "page_rows": 50,
       "page_headcount_sum": 50,
       "whole_filter_expected_sum": 51,
       "response_keys": ["count", "next", "previous", "results"]
     }
     ```
   - اثبات می‌کند برای ۵۱ ردیف، مقدار محاسبه‌شده در کلاینت ۵۰ بوده در حالی که انتظار مستقل ۵۱ است.

## ۴. برنامه آزمون پذیرش (Acceptance Test Plan for Stage 5)

برای تأیید نهایی این نیازمندی پس از اصلاح، سناریوی آزمون زیر باید اجرا و پاس شود:
1. **داده آزمون (Fixture):** ایجاد حداقل ۵۱ رکورد فعالیت روزانه تأییدشده با دو واحد اندازه‌گیری متفاوت (مثلاً متر مربع و متر مکعب)، حداقل یک مقدار ثبت‌نشده (null)، دو پیمانکار با عناوین شغلی مشابه، و `page_size=50`.
2. **آزمون پیجینیشن و جمع کل:**
   - در صفحه ۱، تعداد کل باید ۵۱ و سرجمع نفرات دقیقاً ۵۱ باشد.
   - با کلیک روی صفحه ۲ (که شامل ۱ رکورد است)، سرجمع نفرات در نوار بالا **همچنان بدون تغییر برابر ۵۱** باقی بماند.
   - احجام به تفکیک واحد اندازه‌گیری محاسبه شده و هرگز واحدهای ناهمگن (m2 و m3) با یکدیگر جمع نشوند.
3. **آزمون تطبیق اکسل:** خروجی دانلود شده اکسل (FILE 1) باید حاوی ۵۱ سطر داده باشد و مجموع ستون‌های آن دقیقاً با ارقام نمایش‌داده‌شده در نوار بالای UI یکسان باشد.
4. **آزمون بازسازی URL:** لینک فیلترشده در یک مرورگر جدید یا تب ناشناس باز شود؛ فیلترها، صفحه و مجموع ارقام دقیقاً یکسان بازیابی شوند.
5. **آزمون فیلترهای روزانه:** در صفحه گزارش‌های روزانه، فیلتر دیسیپلین، بلوک و پیمانکار اعمال شده و گزارش‌های مرتبط با آن فیلتر بازگردانده شوند.
