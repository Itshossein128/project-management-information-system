## Clarifications

### Session 2026-11-13

- Grounded in predecessor clarifications and stakeholder decisions already recorded across A.7 (`051`–`055`):
  - **Parentless summary/milestone rows and zero-duration tasks in `real-data/plan.mpp` (P3 decision, 2026-11-12)**: Parentless rows `شروع` and `پایان` are omitted from stored schedule activities with explicit row-level `activity_without_parent` warnings; zero-duration tasks with a valid parent remain stored as milestones (`milestone = true`, `duration_days = 0`); summary predecessor links (`8055`, `8084`, `8102`, `8120`) are skipped with `predecessor_is_summary` warnings; source calendar application limits are reported via `calendar_not_applied`; stored reference counts on `real-data/plan.mpp` are **6 WBS nodes, 72 activities, and 72 relationships**.
  - **Upload byte retention and purge policy (P5 decision, 2026-11-12)**: Original uploaded schedule bytes are retained for **7 days (168 hours)** after terminal attempt completion (`completed` or `failed`) for support and reproducibility diagnostics, after which only the raw upload payload is purged while durable job metadata, warnings, errors, and audit records remain intact.
  - **Project status governance (P1 interpretation `M03`)**: Project lifecycle statuses remain a governed state machine (`draft`, `pending_approval`, `active`, `suspended`, `completed`, `archived`) rather than an open user-editable dictionary, while organizational units, contract types, measurement units, and WBS templates operate as governed reusable reference catalogs.

Without verifying that P1–P5 handoffs are genuinely complete and without reconciling every one of the 56 audit items against current-version evidence, any downstream acceptance claim or employer package would be unreliable.

### User Story 2 - End-to-End Positive Reference Project Journey Across Roles (Priority: P1)

A project planner, an independent approver, an organizational administrator, and a system administrator need to execute the complete positive lifecycle of a reference construction project (`D03`) in a real browser against a live backend and worker—from initial draft creation, governed reference selection, charter approval, controlled change request, multi-level WBS authoring, and template copy through schedule preview, native `real-data/plan.mpp` append import, repeat import, safe replacement, four-date schedule inspection, and full lifecycle transitions (suspend, resume, complete, undo completion, archive, and restore from archive).

**Why this priority**: Individual unit or phase tests do not prove that a real project can travel uninterrupted from draft registration through WBS setup, asynchronous schedule import, baseline/date tracking, and archival recovery across separated user roles in the integrated application.

**Independent Test**: In an isolated acceptance environment with real browser sessions and running backend/worker services, execute the 10-step positive journey on a dedicated test project using separated role accounts and `real-data/plan.mpp`, verifying UI outcomes, persisted database state, audit logs, and reconciled schedule figures at each transition.

**Acceptance Scenarios**:

1. **Given** an authenticated project creator/planner and active organizational reference catalogs (organizational units, contract types, measurement units), **When** the user creates a new project in `draft` (`پیش‌نویس`), selects governed reference values, completes all 6 kickoff charter sections (`منشور آغازین`), and submits for approval, **Then** the creator is prevented from self-approving (Separation of Duties), and an independent approver can approve the charter only when activation gates (assigned project manager, defined scope, valid budget ceiling > 0) are satisfied, transitioning the project to `active` (`فعال`) with an immutable approval audit record.
2. **Given** an `active` project with approved baseline fields, **When** a planner submits a formal change request (`درخواست تغییر رسمی`) for a protected project attribute and an independent approver approves or rejects it, **Then** active project values remain unchanged while pending or rejected, and upon approval the target field updates atomically with before/after values, requester, decider, and timestamp recorded in history.
3. **Given** an `active` project, **When** the planner creates a WBS hierarchy of at least 3 levels with code, name, parent, sort order, weight/share, responsible person, and completion criterion, moves/renumbers a node, saves a WBS template, and applies that template to a second independent project, **Then** the hierarchy preserves parent-child integrity and 100% sibling weight rules, and subsequent edits in the first project or template do not mutate the second project's WBS.
4. **Given** `real-data/plan.mpp` (SHA-256 `3a4f800f0f57e408be52095117f1a53887f653ac07f720621b3e22aa67765553`, 777,216 bytes) and representative MSP XML / Primavera P6 XER fixtures, **When** the planner runs preview and then confirms an `append` (`افزودن / به‌روزرسانی`) import through the real asynchronous worker, **Then** the stored project state reconciles to **6 WBS nodes, 72 activities, and 72 relationships**, milestones and converted workday lags (`480` min/day) are preserved, and explicit structured warnings are visible for omitted parentless rows (`activity_without_parent` on `شروع` and `پایان`), skipped summary predecessors (`predecessor_is_summary` on UIDs `8055`, `8084`, `8102`, `8120`), and unapplied calendars (`calendar_not_applied`).
5. **Given** a project where `real-data/plan.mpp` has already been imported via `append`, **When** the planner imports the same file a second time in `append` mode, **Then** the attempt completes with `nothing_changed = true`, zero duplicate WBS nodes, activities, or relationships are created, and no redundant empty baseline version is generated.
6. **Given** a project with protected execution history (such as a locked/approved baseline, progress records, period reports, schedule change requests, or measurement records) versus a clean unprotected project, **When** the planner attempts `replace` (`جایگزینی ایمن`), **Then** replacement is blocked with `baseline_replace_forbidden` on the protected project leaving all records intact, whereas on the unprotected project (after explicit confirmation) prior schedule rows are soft-deleted and replaced while preserving import/audit history.
7. **Given** an imported project schedule with an approved baseline, **When** the user inspects schedule views (table, Gantt, WBS summary), **Then** the 4 activity date sets (approved baseline, current planned, actual, forecast), milestone indicators, delay variance against the approved baseline, and critical-path status/validity warning (when network prerequisites are incomplete) are displayed consistently across views.
8. **Given** an `active` project containing WBS nodes, activities, relationships, and baselines, **When** authorized users transition the project through `suspended` (`متوقف`) → `active` (`فعال`) (with mandatory reason and confirmation), `completed` (`تکمیل‌شده`) → `undo-complete` (by system administrator only), and `archived` (`آرشیو`) → `restore` (by system administrator only), **Then** each reversal restores the exact `previous_status` and all project, WBS, schedule, baseline, and charter records remain intact without data loss.

### User Story 3 - Independent Negative, Adverse, Concurrency, and Access-Boundary Journeys (Priority: P1)

An acceptance tester needs independent negative and boundary scenarios (`D03`) executed and evidenced so that invalid inputs, structural cycles, malformed/oversized files, mid-flight cancellations, network drops, duplicate submissions, mid-queue permission/lifecycle changes, cross-project tampering, and role restrictions fail safely with clear user-facing diagnostics and zero data corruption.

**Why this priority**: Acceptance of a mission-critical project and schedule management module requires proving not only that valid inputs succeed, but that adverse operations cannot corrupt existing project schedules, bypass role boundaries, or strand users in unrecoverable states.

**Independent Test**: Execute the catalog of negative, concurrency, and access-boundary scenarios against the live stack and verify that every rejected or interrupted action leaves pre-existing project, WBS, activity, relationship, and baseline counts unchanged and surfaces a structured, localized error code and recovery path.

**Acceptance Scenarios**:

1. **Given** project, WBS, or schedule editing forms and APIs, **When** a user submits a duplicate/invalid code, a parent node belonging to another project, a direct or indirect WBS/dependency cycle, an impossible date range (`finish < start`), a manual non-milestone activity with zero duration, or a missing/summary predecessor, **Then** the system rejects the mutation with a specific validation code and leaves stored data untouched.
2. **Given** the schedule import workflow, **When** a user uploads an empty file, a corrupted file, a non-schedule file with a renamed extension, a password-protected file, or a file exceeding the 50 MB limit, **Then** the upload is rejected before mutating project data and displays an actionable Persian/English error message with a single-step reset to select a valid file.
3. **Given** a completed import preview showing warnings or discrepancies, **When** the user cancels before confirming import, **Then** no import job is queued and zero changes occur in project WBS, activities, relationships, or baselines.
4. **Given** an active asynchronous import job, **When** the browser loses connectivity or reloads mid-flight, or the user attempts a second submit, file re-selection, or drag-and-drop while the job is active, **Then** duplicate submissions are blocked (`import_already_active` / disabled controls) and the UI reconnects to the existing attempt upon reload until terminal completion.
5. **Given** an import job that was queued while the user had permission on an `active` project, **When** the user's permission is revoked or the project is transitioned to `archived` or deleted before worker execution finishes, **Then** the worker re-validates authorization and project state at execution/commit time, aborts the import, and writes zero schedule records.
6. **Given** two independent projects (Project A and Project B) and users with Viewer (`view_only`), Planner, Approver, and non-member System Administrator roles, **When** cross-project identifiers are supplied or restricted actions are attempted, **Then** cross-project access is denied (`403`/`404`), Viewers cannot mutate or import data, archived projects reject all mutations and imports across UI and API, and non-member System Administrators can observe project views (`A.6` exception) and perform only authorized administrative lifecycle recoveries (`undo-complete`, `restore`).

### User Story 4 - Bilingual, Responsive, Keyboard, and Operational Continuity Verification (Priority: P1)

Users operating in Persian (`fa`, RTL) or English (`en`, LTR), on desktop or mobile viewports, or via keyboard navigation—as well as operations teams relying on real queue/worker resilience and 7-day diagnostic retention—need verified continuity across the integrated candidate build.

**Why this priority**: UI regressions in RTL/LTR layout, inaccessible dialogs, or drift between the P5 operational container image and the P6 candidate code would invalidate acceptance even if core API logic passes.

**Independent Test**: Verify primary project, WBS, and schedule import journeys in both `fa` (RTL) and `en` (LTR), at desktop and mobile widths, and via keyboard-only interaction, and verify that P5 operational evidence (real RabbitMQ/Celery worker, crash recovery, resource containment, and 7-day byte purge) matches the exact P6 candidate tree or is re-executed on any updated tree.

**Acceptance Scenarios**:

1. **Given** the project management, WBS, and schedule import screens, **When** switched between Persian (`fa`, RTL) and English (`en`, LTR), **Then** all labels, status badges, warning codes, and recovery actions render in the active locale without raw translation keys or broken directional alignment.
2. **Given** desktop (`1280px+`) and mobile (`375px`) viewports and keyboard-only navigation (`Tab`, `Shift+Tab`, `Enter`, `Escape`), **When** a user navigates project lifecycle controls, WBS forms, and the schedule import modal, **Then** focus order is logical, dialogs trap and restore focus properly, and primary actions remain reachable without clipped controls.
3. **Given** the P5 operational verification evidence (`specs/055-a7-p5-import-operations/evidence/verification.md` and `reproduction.md`), **When** evaluated against the P6 candidate commit/tree SHA, **Then** any code change touching schedule/import/project runtime since P5 triggers a fresh verification on the updated candidate tree so operational and functional evidence share a single consistent baseline.

### User Story 5 - Self-Contained Employer Delivery Package and Honest Acceptance Record (Priority: P1)

An employer representative (`نماینده کارفرما`) or independent acceptance auditor needs a self-contained, reproducible delivery package (`D04`)—including exact version identifiers, environment startup/reset commands, hashed reference schedule files with control figures, a secret-free role access guide, a concise Persian test guide, a step-by-step scenario & defect checklist, and an honest 4-category status summary—to execute acceptance testing independently without developer intervention.

**Why this priority**: Contract milestone R0 and audit item `D04` require delivering a verifiable acceptance package where the employer can independently run the scenarios and record sign-off, with a strict separation between engineering verification and actual employer approval.

**Independent Test**: Hand the delivery package in `specs/056-a7-p6-delivery-acceptance/` to an independent operator or reviewer; verify that every file path, SHA-256 digest, control count, role instruction, and step-by-step Persian scenario can be followed end-to-end without missing prerequisites or exposed secrets, and that the employer sign-off section remains honestly separated from technical readiness.

**Acceptance Scenarios**:

1. **Given** the completed P6 delivery package, **When** an auditor inspects its metadata and reference assets, **Then** it specifies the exact candidate commit/tree SHA, environment identifier, startup and clean-reset procedure, and SHA-256 digests + byte sizes + control figures (file vs preview vs stored) for `real-data/plan.mpp` and all XML/XER acceptance fixtures.
2. **Given** the role matrix in the delivery package, **When** an operator prepares accounts for acceptance testing, **Then** instructions cover all 5 required personas (Project Creator/Planner, Independent Approver for SoD, Viewer, System Administrator, Organizational Reference Steward) without embedding raw production passwords, tokens, or personal names in repository artifacts.
3. **Given** the executive summary in the delivery package, **When** reviewed by the employer, **Then** all in-scope A.7 capabilities and 56 audit items are transparently categorized into the 4 required buckets: «قبلاً موجود و تأییدشده روی نسخه حاضر», «در A.7 اصلاح/تکمیل شد», «هنوز باز/اجرانشده», and «قابل تست توسط کارفرما».
4. **Given** the acceptance sign-off sheet in the delivery package, **When** technical verification concludes before formal employer review, **Then** the package records «آماده پذیرش فنی» (or the exact blocked status if any gate remains open) while leaving the employer's final decision, date, and role title fields unfabricated for the employer representative to complete.

### Edge Cases

- **Open Predecessor Handoff Gate (`055` `T049`)**: If a predecessor phase's handoff explicitly marks a gate open (such as P5 `T049` requiring a second independent operator to run the clean reproduction on the current image), P6 must record that open gate transparently and must not claim unconditional P6 closure until the predecessor gate is closed in its owning scope.
- **Standalone Traceability Artifact Gaps in Predecessors (`052`, `053`)**: Where P2 and P3 recorded audit mappings inside `handoff.md` and `evidence/verification.md` instead of standalone `traceability.md` files, P6's master traceability matrix must cross-reference the exact evidence files and verify whether backfilling standalone predecessor files is needed during convergence.
- **Predecessor Defect Discovery During Integrated Testing**: If an end-to-end browser or API test reveals a bug in P1–P5 logic (e.g., charter SoD, atomic import rollback, parser mapping, UI recovery, or worker cleanup), remediation must return to the owning feature directory (`051`–`055`), update its tasks/evidence via `/speckit-converge`, and then re-run integrated P6 verification on the resulting tree.
- **Repeated Acceptance Runs on the Same Environment**: Running the employer test guide multiple times must not fail due to residual project codes, locked active imports, or mutated reference templates; the delivery package must provide a deterministic project isolation or reset procedure.
- **Sensitive Reference Data (`real-data/plan.mpp`)**: Acceptance evidence and employer guides must cite SHA-256 hashes, aggregate counts, and permitted warning codes (`activity_without_parent`, `predecessor_is_summary`, `calendar_not_applied`) without dumping full proprietary schedule text or raw binary payloads into markdown reports.

- **FR-004 (Reference Schedule Figure Reconciliation — `D03`)**: For `real-data/plan.mpp` (SHA-256 `3a4f800f0f57e408be52095117f1a53887f653ac07f720621b3e22aa67765553`) and acceptance XML/XER fixtures, verification evidence MUST reconcile source file counts, preview counts, import result counts, and stored database counts—specifically confirming **6 WBS nodes, 72 activities, 72 relationships**, omitted parentless `شروع`/`پایان` rows (`activity_without_parent`), skipped summary predecessors `8055`/`8084`/`8102`/`8120` (`predecessor_is_summary`), and `calendar_not_applied` warnings.

### Key Entities *(include if feature involves data)*

- **Audit Disposition Record (`رکورد وضعیت ممیزی ۵۶گانه`)**: Maps each audit ID (`P01`–`D04`) to its source requirement, owning phase (`A.7-P1` through `A.7-P6`), current candidate verification evidence, and disposition status (`تأیید فنی`, `ناقص`, `اجرانشده`, `نیازمند پاسخ کارفرما`).
- **Acceptance Scenario Execution Record (`رکورد اجرای سناریوی پذیرش`)**: Captures scenario ID, positive/negative/boundary classification, role persona, input fixture/hash, expected result, observed UI/API/DB result, pass/fail status, and evidence artifact path.
- **Reference Schedule Reconciliation Ledger (`جدول تطبیق فایل مرجع زمان‌بندی`)**: Links each reference file (`real-data/plan.mpp` and XML/XER fixtures) by SHA-256 digest and byte size to its source counts, preview counts, import result summary, stored DB counts, and expected warning codes.
- **Employer Delivery Package (`بسته تحویل و پذیرش کارفرما`)**: Self-contained bundle of candidate build metadata, environment setup/reset guide, role matrix, Persian step-by-step test guide, 4-category status summary, defect log, and unfabricated employer sign-off sheet.
