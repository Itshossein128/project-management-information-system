# Contract: Contained Import Preparation and Runtime Profile

Design for Linux delivery; implementation and empirical calibration are still required.

## Launcher protocol

The API preview/new-start validator and Celery import preparation call the same internal launcher. An authorized in-flight start match returns the existing job before any launcher/capacity admission. It reserves a global `ImportProcessingSlot`, creates a random-token 0700 workspace on the configured bounded scratch mount, and prepares a delegated per-execution cgroup before releasing any untrusted bytes to the helper. Verify effective controller values, filesystem capacity and ownership; missing controls fail closed with `conversion_failed`.

The helper is a fresh exec/spawn Python process in a new process session, with a minimal allowlisted environment (Java/classpath/locale and scratch settings only), no DB/broker credentials, and no inherited database connections. Do not initialize JVM in API/worker or fork an initialized JVM. No threaded `preexec_fn`. A launch handshake keeps the helper blocked until containment membership is verified.

Use fixed input/output names and a bounded versioned JSON prepared-data protocol with explicit task/relationship fields; validate types, lengths, dates, decimals and maximum serialized size before reconstruction. Reuse P3 parser/resolve data structures; do not deserialize pickle or executable input. XML/XER parsing uses the same preparation boundary; database-dependent safety and annotation stay under the parent's final project lock. Refactor existing execute functions minimally to accept trusted server-produced prepared input rather than reparsing unbounded data inside application.

JPype initializes its JVM inside the helper. If packages/classpath make that route unavailable, the configured CLI route may run inside the same containment group and original conversion deadline. Do not retry a timeout/resource failure through another route. Set consistent heap/JVM arguments for both routes. Route/version is recorded as restricted metadata for reproducibility.

## Initial isolated acceptance profile

All values are technical safety settings, not a customer SLA or a claim that every 50 MiB input succeeds.

- Existing upload cap: 50 MiB.
- `MPP_CONVERT_TIMEOUT_SECONDS`: 60 seconds total, including helper/JVM startup and any fallback.
- Proposed `IMPORT_PREPARE_TIMEOUT_SECONDS`: 75 seconds total, including parsing/serialization and cleanup; conversion deadline is nested within it. If conversion setting changes, validate remaining preparation/request budgets rather than allowing an inconsistent profile.
- Helper cgroup: memory.max 1 GiB; memory.swap.max 0; memory.oom.group enabled; pids.max 32; cpu.max quota equivalent to one CPU. JVM heap maximum 512 MiB. Heap cap alone is not the memory boundary.
- Dedicated scratch filesystem quota: 256 MiB across admitted work, with no fallback to unrestricted `/tmp`; converted XML/prepared output cap: 128 MiB each subject also to aggregate scratch quota; diagnostics cap: 64 KiB; no unbounded PIPE capture or whole-file read before size checks.
- Global admitted preparation slots: one in the isolated acceptance profile. Preview/new starts without an in-flight match must reject busy rather than wait indefinitely; queued jobs wait within their dispatch deadline. Capacity is not inherited from general Celery concurrency.
- Process termination grace: 2 seconds within preparation budget; force kill group/cgroup if needed, reap known direct children, verify containment empty before cleanup/release.
- Import execution soft/hard limit: 170/180 seconds; absolute claim deadline 180 seconds. Preparation, lock waiting and application share this budget. Application statements use at most 90 seconds and remaining attempt budget; locks wait at most 3 seconds. Parent checks absolute deadline throughout apply; worker hard termination is the final rollback boundary, not the only timeout mechanism.
- Gunicorn timeout: 90 seconds for the complete synchronous preparation/response path, upstream gateway greater than 90 seconds. Current production value 60 must not silently survive rollout. Request-disconnect handling must also terminate preparation and clean up.
- Pending dispatch deadline: 300 seconds; maintenance interval: 60 seconds; Redis visibility timeout: 600 seconds (broker transport, result-backend transport, and app visibility_timeout consistently set; separate Redis instance prevents other applications overriding the effective timeout). Maintenance lock wait is bounded and skips live locked applies. Batch size is at most 100 items; the finite-cohort protocol below drains consecutive batches without a full-interval pause and without extending job deadlines.
- Original purge scan: hourly; expiry is exactly anchor + 168 hours. Catch-up maintenance runs on restoration before new admission. Report backlog/lag; do not claim a universal cleanup completion SLA when service or database is unavailable.

The helper root's cgroup delegation and scratch mount are deployment prerequisites. Never expose the whole cgroup filesystem or Docker socket to the API. Deployment documentation must grant the minimum subtree/controller access or record a readiness blocker. Existing tools/technology remain; no new public service/API is introduced. Run controlled acceptance first; if JVM cannot start within the profile, deliberately revise effective settings with measured evidence and rerun both success and limit-enforcement cases.

## Parent loss and restart

The execution token, host/reboot identity, containment identifier and deadline are recorded before work starts. Parent death cannot remove memory/disk bounds. Normal supervisor timeout kills the complete containment, including CLI descendants. A helper-local monotonic watchdog and parent-death handling provide additional termination; maintenance independently kills expired owned cgroups after verifying the token/host identity. PID alone is never trusted. The deadline and maintenance recovery window cover abrupt supervisor death; tests must prove no orphan conversion remains after recovery.

Maintenance quarantines a slot if it cannot verify/terminate an expired containment; it must not simply free capacity while leaked work remains. Restart scanning touches only manifests under the dedicated root and token-named delegated subtree, refuses symlinks, and confirms no active owner before deletion. A host reboot leaves no live old processes but still requires manifest/file cleanup.

## Required evidence

Actual native reference preview/import under this profile; selected route and versions; peak memory and scratch/output; timeout kills (including fallback descendants); memory/output/disk exhaustion; parent/worker loss; safe maintenance/restart; exactly one committed application per job; unrelated/active files preserved; and a healthy import after every failure. Service/executable inventory and simulated tests do not establish these outcomes.

## Finite-cohort maintenance and verifiable bounds

These are initial engineering safety budgets, not a customer SLA. They assume the database, required filesystem/cgroup controls and a maintenance executor remain healthy throughout the measured interval; unavailable service or exceeded maintenance budgets are explicit failures, never a passing completion claim.

- A single maintenance leader per isolated scope takes a stable cutoff and an oldest-first paged cohort ordered by original due/deadline, then family/UUID/token. Recovery includes affected pending/running jobs and owned abandoned workspaces; purge includes originals already expired at the cutoff. Let N include all outstanding items ahead of or within that cohort, including deferred rows; record N without loading source bytes. New arrivals belong to a later cohort and cannot overtake it. Use an exclusive bounded leader guard so overlapping Beat/command runs cannot reset the cutoff or duplicate destructive work.
- B=100 is a maximum batch size, not one batch per timer tick. Drain the same cohort through consecutive batches, with inter-batch delay G≤1 second. An item that cannot be locked is retained in a deferred queue and revisited; a cursor must never silently discard it. No fresh-work admission occurs during restart catch-up until that cohort completes or an explicit blocked state is reported.
- Enforce per-item maintenance wall-clock budget C=10 seconds, including lock wait (≤3 seconds), termination grace (≤2 seconds), metadata/cleanup and bounded diagnostics. Index/paging/selection overhead is charged to these budgets or G, not left as unbounded hidden scan work. A budget overrun/DB timeout/unverifiable containment fails the pass, quarantines unsafe capacity as appropriate and keeps restart admission closed; it is not counted as a completed item. Persist/report unfinished identities and retry fairly on restored service.
- For recovery, a pre-existing pending attempt may still use its dispatch window D=300 seconds followed by execution E=180 seconds. Conservatively allow L=D+E=480 seconds for these existing lifecycles/locked work; do not expire a live claim early. Remaining closed-cohort processing is bounded by N*C + ceil(N/B)*G after that allowance, with no deadline renewal on republish or retry delivery.
- From service restoration or scheduled recovery eligibility, the documented recovery/abandoned-scratch bound is W_recovery(N)=60+480+10*N+ceil(N/100) seconds. From original-byte expiry, the purge bound is W_purge(N)=3600+480+10*N+ceil(N/100) seconds, where N includes previously queued cohort work ahead of the expired item and the same 480-second allowance covers a recovery cohort already ahead of purge. Startup catch-up starts immediately, so its detection interval is zero rather than 60/3600. Empty cohorts finish without artificial waiting. These conservative bounds require the successful-pass assumptions above; a clock/budget/service violation is a recorded blocker.
- Acceptance must include at least 201 jobs/artifacts across both job families with B=100, arrivals while the first cohort drains, one temporarily locked eligible row, duplicate maintenance invocations and interrupted/resumed cleanup. Check no starvation, no full-interval pause between batches, immutable expiry, preserved active/unrelated input, recorded N/cutoff/timing and completion within the applicable formula. Test budget exhaustion as a failed/blocked pass, not silent deadline extension. Deterministic fixture clocks test timing logic; at least one actual maintenance/worker run must demonstrate draining.
