## User Scenarios & Testing *(mandatory)*

### User Story 1 - Official Daily Report Header, Weather, Shift Hours, and Reference-Form Layout Parity (`FILE 4`) (Priority: P1)

A site engineer, technical-office specialist, or resident supervisor exports a project daily report (`FILE 4` Excel and official PDF) for a normal workday, an inactive/holiday day, or a three-shift day and compares it side by side with the agreed Shiraz reference form under the B01 data contract. The report header accurately displays project identity, contract reference, Solar Hijri date, Persian day of week, preparer identity, official report number (`<projectID>-<projectDay>-<YYYY>-<MM>-<DD>`), actual project day, actual worked shift start/end times and effective durations (eliminating static "not recorded" placeholders), observed weather/temperature/wind/ground conditions, 3-day weather forecast (or explicit `"unknown"` when unavailable), and site active/inactive status with mandatory inactivity reason. Under the selectable Shiraz 34/32 reference-form profile, direct and indirect manpower tables are rendered side by side in adjacent horizontal blocks matching the reference form, while additional, custom, or historical job titles appear in a dedicated appendix without loss; projects not using the Shiraz 34/32 profile render their configurable project catalog without forcing fixed 34/32 counts.

**Why this priority**: Hardcoded shift-hour placeholders (`DEF-B03-01`), vertically stacked instead of side-by-side manpower tables (`DEF-B03-02`), and rigid 34/32 catalog assumptions (`DEF-B03-08`) are primary blockers to reference-form parity (`H01`–`H04`, `D06`, `D08`, `E01`–`E03`, `X07`).

**Independent Test**: Export `FILE 4` Excel and PDF for (a) the reference day `SIM-A1-001` (`1406-03-01`, project day 12) with two worked shifts (one recorded duration, one unknown duration) and custom/extra job titles, (b) a three-shift active day, (c) an inactive/holiday day with a valid inactivity reason, and (d) a project with a custom non-Shiraz job catalog. Verify header identity parity across screen, Excel, and PDF; verify actual shift start/end/duration rendering; verify side-by-side direct/indirect manpower layout and appendix placement under the Shiraz 34/32 profile; and verify custom catalog preservation without forced 34/32 slots.

**Acceptance Scenarios**:

1. **Given** a daily report with project identity, contract reference, Solar Hijri date, actual start date, preparer, and worked shifts (`1`, `2`, `3`) with recorded start, end, and actual duration values, **When** `FILE 4` Excel and official PDF are exported, **Then** the header shows identical project, contract, date, day-of-week, preparer, project day, official report number (`<projectID>-<projectDay>-<YYYY>-<MM>-<DD>`), and actual shift start/end/duration values across screen, Excel, and PDF, with no hardcoded "not recorded" placeholder text.
2. **Given** a worked shift whose actual working duration is missing, or unavailable weather-log/forecast data, **When** the daily report is rendered and exported, **Then** the missing shift duration, missing weather-log reading, or unavailable 3-day MET Norway Locationforecast 2.0 forecast is shown explicitly as `"unknown"` / unrecorded without fabricating hours, temperatures, wind/ground readings, or forecasts.
3. **Given** a daily report with valid weather conditions (five standard states, temperature within `-40` to `+60` °C with min ≤ max, multiline weather impact notes) or an inactive site day with one of the five standard inactivity reasons, **When** saved and exported to Excel and PDF, **Then** invalid weather states or out-of-range/inverted temperatures are rejected, inactivity without a reason is rejected, active days retain no stale inactivity reason, positive activity on an inactive day requires explicit user confirmation (cancelling saves nothing), and multiline weather notes are preserved verbatim.
4. **Given** a project using the selectable Shiraz 34/32 reference-form profile with both standard titles and additional, custom, or historical job titles, **When** `FILE 4` Excel is exported, **Then** direct and indirect manpower tables are laid out side by side in adjacent horizontal blocks matching the reference form, column totals match source counts without conflating row sums with unique persons or `نفرروز`, and all additional, custom, and historical titles appear intact in a dedicated appendix.
5. **Given** a project using a configurable project job-title catalog without the Shiraz 34/32 profile, **When** `FILE 4` is exported after catalog updates, **Then** the export reflects the project's versioned catalog order and preserves historical titles without dropping rows or imposing fixed 34/32 counts.

### User Story 2 - Operational Sections Fidelity: Activities, Machinery (Legacy Null vs. Zero), Materials, Concrete/QC, Issues, HSE Localization, Visits, and Attachments (Priority: P1)

A project reviewer or resident supervisor inspects every operational section of the daily report (screen, `FILE 4` Excel, and official PDF) against the originating unit sub-reports. Executed activities preserve WBS, shift (`1`/`2`/`3`), distinct contractor vs. crew attribution, location (parcel, block, floor), and measured zero vs. unknown quantity semantics. Machinery counts each uniquely identified asset once across its five statuses, enforces stoppage reasons and the 24-hour daily ceiling, and preserves unknown (`null`) operating hours on legacy equipment rows as blank/dash in BOTH Excel and PDF while keeping explicit `0` as numeric `0`. Materials display only actual site receipts in the main receipt table while keeping consumption, returns, waste, and warehouse-document reconciliation separate. Concrete pours display all contract-mandated summary columns (volume, location, delivery note, lab sample code, sampling state) alongside clear drill-down paths for deeper QC details (batching plant, truck mixer, lab sheet number, slump, and the link to 28-day test results). General activities, obstacles/issues (with owner and due date), structured visits/meetings, and validated JPEG/PNG attachments preserve structure, ordering, project boundaries, and fully localized Persian labels (eliminating raw English HSE labels such as `Major` and `safety` in Persian exports).

**Why this priority**: Fabricating `0` for unknown legacy equipment hours (`DEF-B03-05`, historical strict XFAIL), omitting concrete/QC print and drill-down fields (`DEF-B03-06`), and leaking raw English HSE labels (`DEF-B03-07`) directly violate semantic accuracy and bilingual reference-form parity (`D04`, `D09`–`D17`).

**Independent Test**: Construct a daily report covering activities (including explicit `0.00` and unset), a legacy equipment row with unknown hours alongside an explicit `0`-hour row, material receipts plus consumption/return/waste reconciliation against a specific warehouse document, a concrete pour with sampling/QC metadata, an obstacle with owner and due date, a high-severity HSE incident, a structured site visit, and a valid/invalid attachment attempt. Export Excel and PDF in Persian and verify zero fabricated zeros, complete concrete/QC columns and drill-down references, 100% localized Persian HSE severity/type labels, and rejection of cross-project or invalid attachments.

**Acceptance Scenarios**:

1. **Given** a daily report containing a legacy equipment row with unknown (`null`) operating hours and another equipment row with explicit `0` operating hours, **When** `FILE 4` Excel and official PDF are exported, **Then** the unknown row is displayed as unknown/blank/dash (never `0`) in both Excel and PDF, while the explicit `0` row remains numeric `0` in both outputs.
2. **Given** executed activity rows with WBS, shift, contractor, crew, location, and quantities, **When** validated and exported, **Then** contractor and crew remain distinct fields (never substituted for each other), invalid or cross-project WBS/contractor references are rejected, explicit `0`/`0.00` quantities remain numeric zero, and unset/not-measured quantities remain unknown.
3. **Given** machinery logs across multiple reporting units for the same date, **When** summarized and exported, **Then** each uniquely identified machine is counted once across the five standard statuses, stoppages without a reason and daily hours exceeding 24 hours are rejected with localized bilingual errors, and stoppage/repair hours match source records.
4. **Given** material receipts alongside material consumption, returns, waste, and a referenced warehouse document, **When** displayed and exported, **Then** only actual site receipts appear in the main material-receipt table (consumption, returns, and waste never appear as receipts), and reconciliation (`match`, `mismatch`, or `insufficient-data`) compares strictly against the referenced warehouse document rather than general historical stock balance.
5. **Given** concrete pour records with volume, parcel/block/floor/structural element, delivery note, lab sample code, sampling state (`taken`, `not taken`, `unknown`), and deeper QC details (batching plant, truck mixer, lab sheet number, slump, and the link to 28-day test results), **When** exported and viewed, **Then** all contract-mandated summary columns match the source record and print cleanly, while deeper QC details not printed on the summary sheet have an explicit drill-down path and contract omission rationale.
6. **Given** structured general activities, obstacles/issues with follow-up owner and due date, HSE safety incidents (such as `Major` severity and `safety` type), and structured visits/meetings, **When** exported to Persian `FILE 4` Excel and PDF, **Then** structured rows retain their fields, order, and source attribution (never flattened into free text), simple notes are not converted into formal issues or formal meeting minutes, and all HSE incident types and severities display native localized Persian labels (zero raw English tokens such as `Major` or `safety` in Persian output) with visible follow-up owner, immediate action, and due date.
7. **Given** an attachment upload for a daily report or activity, **When** a user uploads a valid JPEG/PNG image up to 10 MB versus a disallowed file type (e.g., ZIP/EXE), spoofed MIME type, oversized file (>10 MB), or cross-project file reference, **Then** valid files are accepted and retrievable from their linked section with recorded timestamp, while invalid, spoofed, oversized, or cross-project files are rejected; large photo galleries are not forced into summary print layout.

### User Story 3 - Print-Ready A4 Pagination, Official PDF Signatures, Legal Roles, Watermarks, Metadata Fingerprint, and Formula Safety (Priority: P1)

A project manager, resident supervisor, or employer auditor prints `FILE 4` Excel and the official daily PDF for a large multi-page report (>50 rows) containing long multiline Persian and English descriptions, user text beginning with spreadsheet formula characters (`=`, `+`, `-`, `@`), and draft/approved/revision states. The Excel file prints cleanly on A4 paper fitted to 1 page wide with defined print area, repeating header rows on every page, right-to-left sheet layout, Persian font, wrapped multiline text, and dynamic row heights so no text or number is clipped. The PDF uses the contractual filename (`daily-report-{date}-{shift}.pdf`), places the three-slot signature block at the end of the report, prints each actor's real name, real organizational/legal role title, and readable local timestamp (leaving unperformed stages empty with no fabricated reviewer or fake title), applies a diagonal draft watermark across EVERY page of non-approved versions (removing it completely on approved versions), and displays the metadata-based integrity fingerprint strictly bounded per `C06`. User-supplied text starting with `=`, `+`, `-`, or `@` is neutralized as literal text while internal calculation formulas remain active and error-free.

**Why this priority**: Missing Excel print setup (`DEF-B03-03`) causes unreadable A4 printouts with clipped Persian text, and missing organizational/legal roles or non-standard direct-approval text in PDF signatures (`DEF-B03-04`) block official supervision sign-off (`E04`–`E08`, `E16`).

**Independent Test**: Export `FILE 4` Excel and official PDF for a >50-row report containing long multiline Persian/English text, cells starting with `=SUM(A1)`, `+cmd`, `-1+1`, `@test`, and three workflow states: `draft`, `approved` (via direct approval skipping intermediate review, and via full three-stage approval), and an open `draft` correction revision. Inspect Excel print properties (A4, print area, fit-to-1-page-wide, repeating headers, wrap, row heights, active `SUM` formulas, neutralized user strings) and visually inspect every PDF page (watermark on all non-approved pages, absent on approved pages, signature block at the end with real name + legal role + local timestamp, no fabricated reviewer on direct approval, and bounded metadata fingerprint).

**Acceptance Scenarios**:

1. **Given** a daily report with more than 50 rows and long multiline Persian and English descriptions, **When** `FILE 4` Excel is exported and prepared for printing, **Then** the worksheet has right-to-left direction, Persian font, explicit print area, A4 page setup fitted to 1 page wide, repeating header rows on subsequent pages, text wrapping, and dynamic row heights so zero text or numeric values are clipped or truncated.
2. **Given** a daily report with more than 50 rows in `draft`, `submitted`, `under_review`, `rejected`, or open-revision `draft` state versus `approved` state, **When** the official PDF is exported, **Then** the file uses the contractual filename (`daily-report-{date}-{shift}.pdf`), displays a clear draft watermark on EVERY page of all non-approved versions, removes the draft watermark from ALL pages of approved versions, and places the three-slot signature block at the end of the document.
3. **Given** an approved daily report (both after full three-stage review/approval and after direct approval without an intermediate reviewer), **When** the official PDF signature block is rendered, **Then** every completed stage displays the real actor's name, their real organizational/legal role title, and a readable project-local timestamp, while any unperformed stage (such as skipped intermediate review) shows an explicit unperformed indicator and NEVER displays a fabricated actor name, fake reviewer, or non-contractual placeholder title.
4. **Given** two exports of the same report version with identical header/lifecycle metadata versus a version whose status or approval action changes, **When** the integrity fingerprint is inspected, **Then** identical metadata produces an identical deterministic fingerprint, changed status/approval metadata produces a different fingerprint, and all user-facing and delivery descriptions explicitly identify it as a metadata fingerprint (never claiming a certificate-backed PKI digital signature or whole-body tamper seal, per `C06`).
5. **Given** user-entered text in any exported field starting with `=`, `+`, `-`, or `@` alongside Persian/English multiline text, **When** Excel workbooks (`FILE 4`, `FILE 5`, `FILE 6`, and multi-sheet workbooks) are exported, **Then** every user-entered string is stored safely as literal text (never evaluated as a formula) while all system-generated calculation formulas (such as manpower and activity totals) remain intact and free of formula errors (`#REF!`, `#NAME?`, `#VALUE!`, `#DIV/0!`).

### Edge Cases

- **Normal day, holiday/inactive day, and empty sections**: An inactive/holiday day with zero operational rows MUST still render a complete, valid `FILE 4` Excel and PDF displaying the mandatory inactivity reason without division-by-zero or empty-range formula errors (`#DIV/0!`, `#REF!`).
- **Explicit zero vs. unknown across all exports**: Measured `0` / `0.00` quantities, explicit `0` equipment hours, and `0%` buildings progress MUST render as numeric zero (`0`, `0.0%`), whereas `null` / unset / not-measured quantities, legacy `None` equipment hours, missing shift durations, and `null` progress percentages MUST render as unknown/blank/dash and NEVER as `0`.
- **Three real shifts (`1`, `2`, `3`) & partial worked shifts**: On a day where all three shifts worked, all three shifts and their actual durations appear; on a day where only shifts `1` and `3` worked, unworked shift `2` is omitted from the worked-shifts header list; if a worked shift lacks a recorded duration, duration and person-hours display as unknown rather than assuming default hours.
- **Long multiline Persian/English mixed text and >50 rows**: Descriptions exceeding multiple lines with mixed Persian/English/numbers and tables exceeding 50 rows MUST wrap cleanly without overlapping text, clipped cells, broken bidirectional order, or missing repeating headers across page breaks in both Excel and PDF.
- **Formula-injection payloads in user text**: User-entered descriptions, notes, titles, contractor names, or remarks beginning with `=`, `+`, `-`, `@`, or leading whitespace followed by those characters MUST be neutralized as literal text in every Excel export (`FILE 4`, `FILE 5`, `FILE 6`, and multi-sheet workbooks) while keeping internal `SUM` formulas active.
- **Draft vs. approved vs. open correction revision**: Exporting a draft correction revision MUST display the draft watermark on every PDF page and reflect the revision's preserved B02 metadata (management opinion, weather/site overrides) without altering the superseded approved version's exported output.
- **Unavailable weather logs or MET Norway forecast**: When observed wind/ground logs, project coordinates, or the MET Norway Locationforecast 2.0 service are unavailable (offline, timeout, or out-of-window future date such as `SIM-A1-001` on `1406-03-01` / `2027-05-22`), exports MUST display explicit `"unknown"` / unrecorded indicators and MUST NOT fail export generation or fabricate weather values.
- **Custom/historical job titles & multi-project profiles**: Adding, renaming, or reordering job titles in a project catalog MUST NOT drop historical rows or force fixed 34/32 counts on projects that do not select the Shiraz 34/32 profile; under the Shiraz 34/32 profile, extra/custom/historical titles MUST appear intact in the appendix.
- **Multi-sheet workbook date-range boundaries (`DEL-03`)**: Inverted date ranges (`start > end`), ranges with zero reports, or ranges exceeding safe synchronous export bounds MUST return explicit bilingual validation feedback rather than corrupt workbooks or silent truncation; duplicate/conflicting sheet names MUST be avoided using canonical Solar Hijri date labels.
- **Authorization and cross-project isolation**: Unauthenticated users, users without active project membership and report-view permission (subject to Constitution Principle I), or users requesting another project's daily report, discipline export, standalone PDF, date-range workbook, or attachment MUST be denied server-side.

## Requirements *(mandatory)*

### Functional Requirements

#### Header, Identity, Weather, Site Status & Shifts (`H01`, `H02`, `H03`, `H04`, `X07`, `C03`, `C08`, `DEF-B03-01`)

- **FR-001**: All official daily report outputs (screen summary, `FILE 4` Excel, and official PDF) MUST display identical values for project identity, contract reference, Solar Hijri report date, Persian day of week, and preparer identity (`H01`).
- **FR-002**: Official daily report headers MUST display the B01-ratified official report number (`<projectID>-<projectDay>-<YYYY>-<MM>-<DD>` using the stable project ID, actual project day where actual start date = day 1, and Solar Hijri project-local date with two-digit month and day) and actual project day number, showing an explicit unrecorded/unknown indicator if the project's actual start date is unavailable (`C08`, `H05` handoff).
- **FR-003**: Daily weather handling and exports MUST enforce the five standard weather states, temperature bounds (`-40` to `+60` °C with min ≤ max), verbatim preservation of multiline weather impact notes in Excel and PDF, observed wind and ground conditions sourced from existing weather logs, and 3-day project-location weather forecasts sourced from the free MET Norway Locationforecast 2.0 service—displaying `"unknown"` / unrecorded whenever a reading, coordinate, or forecast is unavailable and never fabricating values (`H02`, `X07`, `C08`).
- **FR-004**: Site active/inactive status MUST enforce the five standard inactivity reasons, reject inactive status without a reason, clear/prevent stale inactivity reasons when active, require explicit user confirmation (saving nothing on cancel) when positive activity exists on an inactive day, and display site status and inactivity reason consistently in screen, Excel, and PDF (`H03`).
- **FR-005**: Official daily report headers MUST list only shifts that actually worked using canonical shift identifiers (`1`, `2`, `3`) and MUST display each worked shift's recorded start time, end time, and actual working duration from the authoritative shift source—eliminating static placeholder text (such as "shift working hours: not recorded") and displaying unknown/unrecorded whenever actual duration is missing (`H04`, `C03`, `DEF-B03-01`).

#### Reference-Form Layout, Manpower Profile & Catalog Separation (`D06`, `D08`, `E01`, `E02`, `E03`, `C04`, `DEF-B03-02`, `DEF-B03-08`)

- **FR-006**: `FILE 4` Excel MUST render a valid, readable right-to-left (RTL) workbook with Persian font and all contract-mandated sections (`E01`, `E02`).
- **FR-007**: When the selectable Shiraz 34/32 reference-form profile (`C04`) is active, `FILE 4` Excel MUST render the direct and indirect manpower tables side by side in adjacent horizontal blocks matching the Shiraz reference form, with accurate column totals/formulas and zero conflation of summed activity headcounts with unique persons or `نفرروز` (`E02`, `D06`, `DEF-B03-02`).
- **FR-008**: Under ratified `C04`, the project's versioned, configurable job-title catalog MUST remain separate from the selectable Shiraz 34/32 reference-form profile: when the Shiraz 34/32 profile is active, any additional, custom, or historical job titles outside the fixed 34/32 slots MUST be rendered intact in a dedicated appendix (never dropped or merged); when another project catalog/profile is used, exports MUST reflect that project's catalog without imposing fixed 34/32 counts (`D08`, `E03`, `DEF-B03-08`).
- **FR-009**: Manpower rows for the same job title across different contractors MUST remain distinguishable in source/detail data, optional leave/overtime fields MUST match source values, and manpower totals MUST accurately sum each column without fabricating counts (`D06`).

#### Operational Sections Fidelity (`D04`, `D09`–`D17`, `C02`, `DEF-B03-05`, `DEF-B03-06`, `DEF-B03-07`)

- **FR-010**: Executed activity rows MUST preserve WBS reference, canonical shift (`1`/`2`/`3`), distinct contractor and crew fields (never substituting one for the other), location (parcel, block, floor), unit, and measured-zero (`0`/`0.00`) versus unknown (`null`/not-measured) semantics, while rejecting invalid or cross-project WBS and contractor references (`D04`, `C02`).
- **FR-011**: Machinery summaries MUST count each uniquely identified machine once across the five standard statuses, enforce mandatory stoppage reasons and the 24-hour daily duration ceiling with bilingual validation errors, and preserve source operating/stoppage/repair hours (`D09`).
- **FR-012**: Legacy equipment rows with unknown (`null`/`None`) operating hours MUST be displayed as unknown (blank or dash, never `0`) consistently in BOTH `FILE 4` Excel and official PDF, while explicit `0` operating hours MUST remain numeric `0` in both outputs (`D10`, `DEF-B03-05`).
