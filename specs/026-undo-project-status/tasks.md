## TDD execution and preservation rules

For each missing behavioral slice: write an assertion that demonstrates the missing requirement, run it and record **observed RED**, implement minimally, then rerun **GREEN** before moving to its next dependent slice. Collection/import failures, unavailable services and a missing route alone are not behavioral RED. Already-correct behavior keeps truthful GREEN evidence; never remove shell guards, loosen fixtures or break production code to manufacture a failure. Refactor only after GREEN and rerun affected checks.

Contract/schema tests precede their changes; intercepted UX tests precede UI changes; actual integration is separately authored/run at the named gate and never stands in for backend concurrency. All write-core authority, exact target/readiness, signed context, idempotent atomic receipt/audit and no-side-effects guarantees are implemented in US1, not postponed to US2/US3/US4. Later phases extend repair/recovery/history and strengthen proof. A US1 demo uses ready projects only; it is not permission to deploy an incomplete whole feature.

Use the scoped runner/database from quickstart (`velora_restore_undo_026`) and real PostgreSQL. Never run competing pytest processes on the same test DB or overlap transactional migration/concurrency gates with API/browser fixtures. Capture true exit codes before displaying logs; do not print JWTs, .env contents or request Authorization headers. Existing typecheck errors must be freshly baselined rather than assumed. Preserve spec/checklist/plan/design, all parent registration/archive docs/tasks, prior dirty work and historical migrations; adapt only affected fixtures/callers needed for the intentional contract/schema change. No commit, push or deployment unless separately requested.

## Dependencies & Execution Order

### Phase and story graph

```text
Setup T001–T004
  → Foundation T005–T018 (strict schema + atomic original events)
  → US1 T019–T034 (secure confirmed three-destination core, ready-project MVP)
  → US2 T035–T050 (full authority matrix + executable repair/drafts)
  → US3 T051–T067 (owned recovery + faults/contention/session proof)
  → US4 T068–T079 (safe visible history + preservation/cache/locales proof)
  → Polish T080–T087 (final-tree delivery evidence)
```

US1 is independently testable after foundation with ready fixtures and complete base write security; US2's repair can be exercised against that core without UI history; US3's fault/retry tests operate directly on the same core and do not require US4 rendering; US4 is a read/preservation/presentation slice over real receipts. Stories share production files and build incremental capabilities, so whole story phases are deliberately sequential rather than falsely labeled independent parallel work. Their acceptance criteria remain separately testable at each checkpoint. No final deployment claim is made at a partial checkpoint.

### Within-story TDD waves and safe parallel opportunities

Only tasks explicitly listed in a same-checkpoint wave may overlap; run dependent writes/tests sequentially and keep real DB processes isolated:

- Setup: after T001, T002 (Python fixture helper) and T003 (browser config) have disjoint files. T004 then aligns actual seed/client fixtures.
- Foundation: T005 source behavior and T006 migration/schema authoring use separate test files. Finish this RED wave before model/migration/original-event mutations; all shared models/service/serializer edits are sequential.
- US1: after T018, T019 API scenarios and T020 authority scenarios can be authored independently. After T026 and core GREEN, T027 mocked UX and T028 actual journey authoring are disjoint. T029–T031 share dependent UI/client/locale contracts and are sequential. No new API/browser run overlaps DB migration/race work.
- US2: after T034, T035 permission/gate and T036 repair contracts are disjoint; T037 mocked UI and T038 actual integration authoring form the second distinct-file wave.
