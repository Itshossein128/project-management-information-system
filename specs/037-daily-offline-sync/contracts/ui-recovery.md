# Contract: user interface, local recovery and rollout

1. In each existing specialty unit page, load effective configuration and previously authorized reference data; allow offline create/edit/delete only in active editable sections. New draft is listed and opens full header and rows in the same unit. Local snapshot and operation are committed atomically before localized success; on failure preserve unsaved user input with actionable error. Missing reference blocks only dependent action.
2. A new or edited pending row has yellow cloud and accessible localized pending text; pending/sending/synced/failed/conflict have distinct text and keyboard-accessible actions in Persian and English. Errors retain stable code, field, client and operation identity through reload/restart. A failure is not a success toast.
3. Locally overlay changes and pending deletes onto server baseline; a refetch must not replace local work. Resolve independent server additions without erasure. A conflict includes complete base, server and local header and section rows, including activity/labor/material, not just scalar fields.
4. Retry edits create a new linked operation and target only that row; prior successful operations are not resent. Network recovery starts sync automatically when actor and permission are valid. Expired claims become recoverable; overlap cannot create duplicate effects or spurious success.
5. `Use server` shows scope and consequence, asks explicit confirmation, and atomically reconciles only related operations/snapshot so discarded work cannot reappear. `Keep my work` previews destination and values, requests authorized formal correction with stable intent, then transfers; it keeps local source and unresolved remainder until destination operation receipts prove success. Display validation, permission, offline and non-current errors without destructive fallback.
6. Queues, cache, drafts and conflicts are scoped by actor, project and unit. Switching account blocks access and automatic replay of previous actor's data. Unknown-owner legacy records are held safely, with no disclosure to another account; only verified ownership allows review.
7. Inventory existing legacy IndexedDB records and schema versions. Convert only provably mapped records, preserve raw evidence and ambiguous payload; no clear database/whole queue during upgrade or resolution. Explicit local deletion identifies exact scope and requires confirmation; it does not imply server deletion.
8. Rollout: first protect legacy paths and deploy compatible server readers/writers with revision tokens; apply/backfill migration and validate; deploy clients able to read old/new schema; enable v2 sync only after compatibility checks. Keep durable receipts and original local data until reconciliation. Disabling v2 halts sends and retains data. Rollback uses verified compatible reader or export/backup and controlled recovery, not blind IndexedDB downgrade or data clearing.
